# ccish: a C-ish compiler for the PLASMA VM

`ccish` compiles a growing subset of C into PLASMA REL modules. It is
at **milestone 1**: a tiny compiler that works end to end. The design
and the plan for growing it are in [approach.md](approach.md). The
target format is described in [../doc/Bytecodes.md](../doc/Bytecodes.md).

## Building and testing

```
make            # builds ./ccish
make test       # also builds ../src/plvm (the C VM), then runs the tests
```

## Usage

```
ccish [-l] [-i] [-o output] input.c
```

* `-o output`: the module file to write. The default is the input name
  without `.c`. To run a module with `plvm`, give it a lowercase name
  with no extension, and run `plvm name` from its directory.
* `-l`: print a listing of the generated bytecode.
* `-i`: print the IR stream that passes from the parser to the
  lowering stage.

Example:

```
$ cat hello.c
int add(int a, int b) { return a + b; }
int main() { puts(pstr("Hello")); puti(add(2, 3)); putln(); return 0; }
$ ./ccish hello.c && ../src/plvm hello
Hello5
```

## The milestone 1 language

* Function definitions and prototypes returning `int` or `void`, with
  `int` parameters. `main` takes no parameters. Its return value is
  ignored.
* Statements: `return`, expression statements, empty statements and
  nested blocks.
* Expressions: integer and character constants, string literals,
  parameters, function calls, binary `+` and parentheses.
* Digraphs `<% %> <: :>`, `/* */` and `//` comments, and LF, CR or CRLF
  line endings.

Anything else gives a "not supported yet" error.

### Strings and `pstr()`

A string literal is stored as a length byte, the characters, then a
NUL. Its value in C is the address of the first character, as usual.
`pstr("text")` gives the address of the length byte instead. That is
the PLASMA (length-prefixed) form, which CMDSYS routines such as `puts`
expect. `pstr()` only accepts a string literal of at most 255
characters.

### Calling CMDSYS

A function that is called but not defined in the file must be one of
the CMDSYS functions in `cmdsys_funcs[]` in `src/parse.c`, such as
`putc`, `puts`, `puti`, `putln` or `heapalloc`. It is imported from
CMDSYS. These are PLASMA's functions with PLASMA's meanings, not C's.
For example, `puts` takes a PLASMA string and adds no newline. The
compiler checks the argument count against the table, so a mistake is
caught at compile time and not at load time.

As in PLASMA, a `void` function returns no value, and an `int` function
returns exactly one.

## Layout

| Path | Contents |
|------|----------|
| `src/main.c` | Command line and error messages |
| `src/lex.c` | Lexer |
| `src/parse.c` | Stage 1: parser, producing IR ops |
| `src/lower.c` | Stage 2: IR ops to PLASMA machine ops |
| `src/peep.c` | Stage 3: peephole optimizer (no patterns yet) |
| `src/asm.c` | Stage 4: encoding, module writer, listing |
| `tests/run/` | Programs, each with its expected output (`.expected`) |
| `tests/errors/` | Programs that must fail; the first line gives the expected message |

## Known limits

* Output has only been tested on the C VM (`plvm`), not yet on a 6502
  VM.
* Compilation stops at the first error.
* No optimization yet. For example, an `int` function always ends with
  a `CN 0` / `LEAVE`, even right after a `return`.
* Nothing checks evaluation stack depth. Deeply nested calls can
  overflow the VM's 32-entry stack.
