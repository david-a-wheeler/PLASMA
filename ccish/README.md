# ccish: a C-ish compiler for the PLASMA VM

`ccish` compiles a growing subset of C into PLASMA REL modules. It has
finished milestones 1 to 7 (integers, `char`, pointers, arrays,
globals, control flow, initializers, `static`, `const`, `volatile`,
`struct` and `switch`), and `enum` and `typedef` from milestone 11. The design and the plan for growing it are in
[approach.md](approach.md). The target format is described in
[../doc/Bytecodes.md](../doc/Bytecodes.md).

**ccish and C.** ccish is a subset of C by design (approach.md,
decision 16):
* What it supports generally behaves as C says, so the same source
  compiles with gcc and means the same thing. Where C leaves a choice
  to the implementation, ccish's choices are listed below (`int` is 16
  bits, `char` is unsigned, and so on).
* Some of C is left out on purpose: parts that are hard to implement,
  or costly in space on a 64K machine, and not needed for ccish to
  compile itself. Examples are floating point, `long`, bitfields, and
  structs over 8 bytes passed or returned by value. Using one is a
  compile-time error.
* Strict compatibility may have to give way so the compiler fits in
  64K. Then the goal is incompatibilities that are documented and
  unlikely to affect real code. Known differences so far:
  - a decimal constant over 32767 (such as `40000`) is the `int` with
    those bits, not a `long` (ccish has no `long`); write `40000u` for
    the `unsigned` one;
  - `unsigned char` is plain `char`: ccish doesn't tell the two apart
    (both are unsigned), so `unsigned char *` and `char *` mix freely;
  - mixing signed and unsigned gives no warning (gcc's
    `-Wsign-compare` would);
  - `enum tag` isn't checked against a definition, so ccish accepts
    some wrong programs (a variable of an enum type never defined).

## Building and testing

```
make            # builds ./ccish, ./ccpp, ./cccomp, ./ccgen and ./ccrel
make small      # builds ./ccpp-small, ./cccomp-small, ./ccgen-small
                # and ./ccrel-small
make test       # also builds ../src/plvm (the C VM), then runs the tests
make measure    # compiles ccish's own source with ccish (ccpp
                # preprocessing it), links ccpp, cccomp, ccgen and ccrel,
                # and reports their sizes and how full ccpp's tables got
                # (needs python3)
```

The same source makes two builds (approach.md decision 21). The full
build, the default, has everything. The small build, for the 64K Apple
II, is made with `-DCCISH_SMALL`: it leaves out `-l`, and checks that
only a compiler bug or a damaged file would fail (`CCISH_CHECKS`: so
far `ccgen`'s check of the blocks it moves; later, diagnostics that a
valid program never triggers); `ccgen -i` is in both. Its `cccomp`
gives no warnings, and each error only its file, line, number and
text, without the name or token it's about (`CCISH_DIAG`). So the small
build should compile only code the full build (or gcc) has already
accepted. It writes exactly the same objects and modules; the tests
check that.
`make measure` measures the small build.

## Usage

```
ccish [-l] [-d] [-i] [-k] [-o output] [-I dir] [-D name[=text]] [-U name] input.c [object...]
```

* `object...`: more objects to link after the source's, such as the
  C library's.

* `-o output`: the module file to write. The default is the input name
  without `.c`. To run a module with `plvm`, give it a lowercase name
  with no extension, and run `plvm name` from its directory.
* `-k`: keep the token stream `output.i` and name file `output.nam`,
  the IR file `output.ir`, and the stream files `output.obj` (one
  stream of tagged records: data, strings and functions) and
  `output.syms` (the symbol summary). The preprocessor writes the
  token stream and name file, the front end turns them into the IR
  file, the back end turns that into the stream files, and the final
  pass turns those into the module; normally they are removed
  afterward, and after an error. Their formats are in
  [CCPP.md](CCPP.md) and [OBJECT.md](OBJECT.md).
* `-l`: print a listing of the generated bytecode (full build only).
* `-i`: print the IR that passes from the parser to the back end, as
  the back end reads it, with each function's source line. The IR ops
  are described in [IR.md](IR.md).
* `-d`, `-I`, `-D` and `-U`: as in doc/ccish-guide.md, 2.1.

Example:

```
$ cat hello.c
int add(int a, int b) { return a + b; }
int main() { __puts(pstr("Hello")); __puti(add(2, 3)); __putln(); return 0; }
$ ./ccish hello.c && ../src/plvm hello
Hello5
```

The passes are also programs of their own, which write the same
module. On the Apple II each will run separately, so that each has
nearly all of memory (approach.md, "B3" and 18.7):

```
ccpp [-E] [-k] [-o output] [-I dir] [-D name[=text]] [-U name] input.c
                                    the preprocessor and lexer: writes
                                    output.i and output.nam
cccomp [-k] [-o output] input       the front end: input.i and input.nam
                                    to output.ir (input.i is removed
                                    unless -k)
ccgen [-i] [-k] output              the back end: output.ir and
                                    output.nam to the stream files (both
                                    are removed unless -k)
ccrel [-l] [-o module] output|@file...
                                    the final pass: links them into a module
```

`ccpp` carries out `#include`, `#define` (object-like and function-like
macros, with `#`, `##` and `__VA_ARGS__`), `#undef`, `#if`, `#ifdef`,
`#ifndef`, `#elif`, `#else`, `#endif`, `#error` and `#line`, knows
`__FILE__`, `__LINE__` and `__CCISH__`, and ignores `#pragma` (CCPP.md,
"Preprocessing"). `-I`, `-D` and `-U` work as usual, for `ccish` too.
`ccpp -E` (full build only) writes the tokens as text instead, as
`gcc -E` does.

### Linking several files

`ccrel` is also a static linker (approach.md issue 11). Compile each
file with `ccpp`, `cccomp` and `ccgen`, then link the objects into one
module:

```
$ ./ccpp main.c && ./cccomp main && ./ccgen main
$ ./ccpp util.c && ./cccomp util && ./ccgen util
$ ./ccrel -o prog main util && ../src/plvm prog
```

* Each object is named by its output name, as given to `ccpp`
  (`main` for `main.obj` and `main.syms`). They are linked in the
  order given: every object's globals, then every object's strings,
  then every object's code. `-o` is required with more than one.
* `@file` names the objects in `file` instead, one per line (a CR or
  LF ends a line, and blank lines are skipped): `ccrel -o prog
  @prog.objs`. The VM's command line holds only 127 characters. The
  names may total 512 bytes, and a link may have 32 objects. It's
  GCC's and the linkers' `@file` syntax, but not their format: theirs
  holds arguments, options included, split at white space and quoted;
  ccrel's holds only names, a whole line each.
* `ccrel` keeps the objects, so after a change only the changed file
  needs compiling again. (`ccish` removes the stream files it makes,
  unless `-k`.)
* A function or global that isn't `static` is shared by every object;
  a `static` one is private to its file, so two files may each have a
  `static` function of the same name. A name may be defined in only
  one object ("multiple definition of"), and every declaration of it,
  in every object, must agree with the others: the parameter count,
  whether it returns a value, the types (through a type hash) and a
  global's size ("conflicting types for"). This holds even for a
  declaration nothing uses.
* A function that no object defines must be a CMDSYS function, which
  is imported, or a PLASMA import (an asm label, or after `#pragma
  plasma import MODULE`; doc/ccish-guide.md, 11.1); a program may
  define its own function of a CMDSYS name, with the same type, and
  calls then go to it. Anything else used and not defined is an
  "undefined reference", including a C library function whose object
  isn't on the link line.
* `main` (not `static`) in any object is the entry point.
* The module exports nothing. Other C names are matched in full, with
  their case, and never reach PLASMA's case-insensitive, 16-character
  symbol table.

### The C library

`lib/` holds a small C library in ccish's C, one object per function,
which `make` compiles into `tests/out/lib/`: `<string.h>` (`strlen`,
`strcmp`, `strcpy`, `strcat`, `strncpy`, `strncat`, `strchr`,
`strrchr`, `memcpy`, `memmove`, `memset`), `<stdio.h>` (`fopen`,
`fclose`, `getc`, `putc`, `fputs`, `fread`, `fwrite`, `remove`,
`fflush`, unbuffered over PLASMA's FILEIO), `<stddef.h>`, and
`<plasma.h>` and `<fileio.h>` (CMDSYS's and FILEIO's tables). ccpp finds its headers
after the `-I` directories. ccrel links whole objects and doesn't
search a library yet, so you name the ones you need after the source
(`ccish -o prog prog.c tests/out/lib/strlen ...`); `start` is the
startup for `main(argc, argv)`. `exit` is declared but not defined: it
has to unwind the VM, which isn't done yet. doc/ccish-guide.md, 11.2,
has the details.

## The language so far

* Types `int`, `unsigned` (`unsigned int`), `char`, `void`, structs,
  pointers to them (`int *`, `char **`, `void *`, `struct node *`,
  ...), and arrays (`int a[10]`, `char *names[4]`, `int m[3][4]`,
  `struct pt pts[8]`).
* Function definitions and prototypes returning any of these but an
  array, with parameters of any type but `void`. A struct parameter or
  return value must be at most 8 bytes (see below). An array parameter
  is a pointer, as in C: `int a[]` and `int a[10]` are `int *a`, and
  `int m[][4]` points to arrays of 4 ints. A prototype and a definition must
  agree on the return and parameter types. `main` takes no
  parameters, or two (`argc` and `argv`, with the library's `start`
  object). Its return value, `& 255`, is the exit status. A function must be declared (by a
  prototype, or its definition) before it is called; C89's implicit
  declarations are an error. The CMDSYS functions are declared already.
* Local variables, declared anywhere in a block, with optional
  initializers (`int a, b = 1, *p = &a;`). A local array's initializer
  takes the same forms as a global's (below), but its elements may be
  any expressions (`int v[2] = {x, f(x)};`), and it runs each time the
  declaration is reached. It compiles to stores into the frame; two
  neighboring `char` constants are stored as one word, and trailing
  zeros use CMDSYS `__memset` when that is shorter.
  Array sizes are constant expressions. They have block scope, and
  an inner block may shadow an outer name. As in C99, the first clause
  of `for` may declare variables, which are in scope only in the loop.
* Global variables of any of these types, declared outside functions
  (`int count, *p, buf[1000];`), anywhere before their first use. They
  are private to the module (not exported), though shared by the files
  linked into it. A local or parameter may
  hide a global of the same name, but a global can't share a name with
  a function or another global.
* `extern`, at file scope: `extern int count;` or `extern char buf[];`
  declares a global without giving it storage. A later definition in
  the same file (`int count = 1;`) gives it storage; otherwise it must
  be defined in another file linked with it (see "Linking several
  files"), or it is an "undefined reference". One that is never used
  needn't be defined. `extern` on a function declaration changes
  nothing. An `extern` with an initializer, and `extern` in a block,
  aren't supported. `sizeof` an array of unknown size is an error.
* Global initializers, computed at compile time and stored in the
  module, so they cost no code. A global without one is zero. A large
  one without one (an array or struct of 256 bytes or more, whose
  address no initializer holds) isn't in the module file at all: the
  module takes it from the heap when it loads, and zeroes it, so the
  file is smaller, and so is the memory needed to load it. It is
  reached through a pointer, a little slower (OBJECT.md, "Zero-filled
  globals"). If the heap can't hold such globals, the program prints
  `not enough memory` and doesn't run.
  - Integers and `char`s: any constant expression (`int n = 3 * 4;`,
    `int size = sizeof(int[10]);`).
  - Pointers: 0, or an *address constant*: a string literal or a
    global's (or `static` local's) address, with any constant indexes
    and members (`&m[1][2]`, `&s.y`, `&ps[1].x`), an array's name,
    casts to pointer types, and `+` or `-` a constant (`buf + 10`,
    `2 + buf`, `"abc" + 1`, `(char *)0xC030`). The expression parser
    folds these in code too, so `buf + 10` is one address push. Casting
    an address to an integer (`(int)&x`) gives "initializer is not a
    constant ccish supports".
  - Arrays: a brace list (`int t[5] = {1, 2, 3};`), with the rest
    zero and an optional trailing comma. The size may come from the
    list (`int t[] = {1, 2};`). A two-dimensional array may have a
    list for each row (`int m[2][3] = {{1, 2, 3}, {4}};`, the rest of
    each row zero), or one flat list. A `char` array may be a string
    (`char s[] = "hi";` has 3 elements), and so may each row of a
    `char` array of arrays (`char kw[][6] = {"int", "char"};`).
  - Structs: a brace list too, over the members in order
    (`struct pt p = {1, 2};`). Arrays of structs and structs holding
    arrays or structs may nest lists at any depth, as in C
    (`struct pt ps[] = {{1, 2}, {3}};`), or use one flat list
    (`{1, 2, 3, 4}` is 2 points). A `char` array member may be a
    string (`{"nut", 40}`). Designated initializers aren't
    supported.
  - A scalar may be in braces (`int x = {5};`).
* `static`:
  - A static local (`static int n = 10;`) keeps its value between
    calls. It has block scope, like any local, but lives in the data
    segment, like a global, so it takes no frame space: a buffer too
    big for the frame can be a static local
    (`static char line[300];`). Its initializer takes the forms a
    global's does, must be constant, and is applied once, when the
    module loads. A `for` loop's declaration can't be static, as in C.
  - On a global or a function, `static` makes it local to the file.
    As in C, `static` after a declaration without it is an error, and
    a later declaration without `static` (or with `extern`) keeps it
    static.
* Structs (`struct pt { int x, y; };`), at file scope or in a block:
  - Members are laid out in order with no padding (the 6502 has no
    alignment rules), as PLASMA's `struc` lays them out, so C can read
    PLASMA's data structures. A member may have any complete type:
    another struct, an array, a pointer (to its own struct too, for a
    linked list: `struct node *next;`).
  - `s.m`, `p->m`, `&s.m`, `sizeof`, arrays of structs and pointers to
    them. A member of a variable compiles like a variable (`s.m` on a
    local is one `LLW`), and one reached through a pointer adds its
    offset (`p->m` is `LLW p CB off ADD LW`, and just `LLW p LW` at
    offset 0). Through a constant pointer, such as a block of I/O
    registers, the offset is added at compile time.
  - A tag can be declared first and defined later (`struct s;`), and a
    tag defined in a block is visible only until the block ends. A
    member of a `const` struct is `const`.
  - A struct whose definition hasn't been seen yet is incomplete: a
    pointer to it is fine, but not a variable, `sizeof`, `->` or
    pointer arithmetic. Using a tag for the first time in a parameter
    list gives a warning, as in gcc, since it is visible only there.
  - Assignment copies the struct (`a = b`, `*p = s`, `c = b = a`). The
    result is the struct assigned to, which isn't an lvalue, as in C.
    Between two variables it is a word move per member word when that
    is no bigger (`LLW b SLW a ...`); otherwise, and always through a
    pointer, it calls `__memcpy(dst, src, n)`: CMDSYS's, or the
    program's own if it defines one, with CMDSYS's type. A struct
    with a `const` member can't be assigned as a whole.
  - Initializers: a flat brace list over the scalar members, as for an
    array (below), and a local may also be initialized from another
    struct (`struct pt b = a;`).
  - A struct of up to 8 bytes can be passed and returned by value,
    as the words of its bytes (first word deepest). A parameter lands
    in the callee's frame in its own layout, with no copy, and a
    returned struct is a PLASMA multi-value return: `struct qr { int
    q, r; }` matches PLASMA's `divmod()#2`. A returned struct is
    stored straight into the variable it is assigned to, and passed or
    returned on with no code (`return swap(p);`); `f().x` saves it to
    a temporary first. Passing a struct needs a prototype.
  - A bigger struct can't be passed or returned by value, which is an
    error (a deliberate limit, to keep the compiler small: pass a
    pointer instead).
  - `union`, whose members all start at byte 0. `==` on structs is an
    error, as in C.
* `enum`: `enum [tag] { A, B = 5, C, };`. A constant is an `int`
  constant expression, so it works in `case` labels, array sizes and
  global initializers; it is one more than the one before unless given
  a value, and must fit in an `int`. An enum type is `int`.
* `typedef`, with `*`s, array sizes and qualifiers
  (`typedef struct node *NodeP;`, `typedef int Vec[3];`,
  `typedef const char *str;`). A typedef name can be used wherever a
  built-in type can, and a function typedef can declare a function or
  a pointer (`typedef int binop(int, int); binop *op;`).
* Enum constants and typedef names have block scope, as in C: one
  declared in a block hides a variable of the same name declared
  outside it, and the other way around.
* `char` is one byte and unsigned (0–255). A value is converted to
  `char` by keeping its low byte when it is stored into a `char`,
  passed as a `char` parameter, returned from a `char` function, or
  cast to `char`. In expressions, a `char` is promoted to `int`, as in
  C. `unsigned char` is the same type; `signed char` isn't supported
  yet.
* `unsigned` (`unsigned int`, `int unsigned`; `signed int` is `int`)
  is 16 bits, 0 to 65535. As in C, when an `int` meets an `unsigned`
  in an operator, the `int` becomes `unsigned` (so `-1 < 1u` is 0),
  and an integer constant is `unsigned` if it has a `u` suffix, or is
  hex or octal and too big for an `int` (`0x8000`). Comparisons, `/`,
  `%` and `>>` on `unsigned` values are unsigned. By a constant, `>>`
  (and `/` and `%` by a power of 2) are done inline; otherwise they
  call small helper functions that the compiler adds to the module
  (one copy each, however many files use them).
* Pointers are 16 bits. `&` takes the address of a variable or of
  `*p`, and `*` reaches what a pointer points to, for reading or
  storing. Pointer arithmetic (`p + i`, `i + p`, `p - i`, `p - q`,
  `++`, `--`, `+=`, `-=`) counts in elements, as in C, and arithmetic
  on a `void *` is an error. Pointers compare unsigned, since
  addresses at or above `$8000` are normal.
* Arrays: `a[i]` is `*(a + i)`, as in C (so `i[a]` works too), and an
  array used as a value is a pointer to its first element. An array
  can't be assigned to. A local array must fit in the function's
  255-byte frame, with the other locals; a bigger one can be global or
  a static local.
* Function pointers, with declarators in C's full syntax
  (`int (*fp)(int)`, `int (*table[3])(int)`, `int (*p)[4]`). A
  function's name used as a value is a pointer to it, as is `&f`;
  `fp(x)` and `(*fp)(x)` call through one, and a function's address
  can initialize a global or static (a table, or a struct's members).
  A function type is only its return type, so a call through a
  pointer checks neither its arguments' count nor their types
  (ccish-guide.md, section 4.12).
* Types are checked as strictly as C requires (GCC 14 does the same by
  default): mixing integers and pointers needs a cast, except for the
  constant 0, and pointer types must match unless one is `void *`.
  This applies to assignments, initializers, arguments, return values,
  comparisons and `?:`.
* `const` and `volatile`, before or after the type (`const char`,
  `char const`) and after a `*` (`char *const p` is a const pointer).
  - A `const` object can't be assigned to or incremented. A pointer may
    gain `const` or `volatile` on what it points to (`char *` to
    `const char *`), but losing one is a warning, as in gcc; deeper
    levels must match (`char **` to `const char **` is an error).
  - Reading a `const` variable (an `int`, `char` or pointer, not
    `volatile`) whose initializer is a constant gives that value at
    compile time: with `const int N = 10;`, `x < N` is
    `LLW x CN 10 ISLT`, and `N * 2` is 20. With
    `volatile char *const SPEAKER = (volatile char *)0xC030;`,
    `*SPEAKER` is `LAB $C030`. `&N` still works. As in C, `N` isn't a
    constant expression, so it can't size an array or initialize a
    global, and a `const int` holding 0 isn't a null pointer.
  - A `volatile` object is read and written just as the program says:
    no access is dropped, merged with another, added, or narrowed, as
    C requires (C11 5.1.2.3, 6.7.3). So `x;` reads a volatile `x`, and
    an assignment's value isn't read back from a volatile object. The
    optimizations that change accesses leave volatile ones alone
    (approach.md issue 25). It is checked as part of the type, as
    above.
* Warnings are printed like errors (`file:line: warning 49: ...`), and
  compilation continues.
* Casts between any of these types. `(void)` discards a value.
* Statements: `return`, `if`/`else`, `while`, `do`, `for`, `switch`,
  `break`, `continue`, `goto` and labels, expression statements,
  empty statements and nested blocks.
* `switch` compiles to PLASMA's `SEL` and a case table after the body,
  sorted by value, 4 bytes per case. `case` and `default` labels may be
  anywhere in the body, even inside nested blocks and loops (Duff's
  device), and cases may be in any order. A case value is an integer
  constant expression (`'a'`, `2 + sizeof(int)`; a `const` variable
  isn't one, as in C). Limits: case values in one switch may span at
  most 32767 (a 6502 VM rule for `SEL`), and at most 36 cases may be
  in the switches open at once (`MAX_CASES`).
* Expressions, with C's precedence and associativity:
  - integer and character constants, string literals, variables,
    function calls and parentheses;
  - unary `- + ~ ! * &`, prefix and postfix `++ --`, indexing
    `a[i]`, and members `s.m` and `p->m`;
  - `sizeof expr` and `sizeof(type)`, where a type may have `*`s and
    array sizes (`sizeof(char *[4])`). The expression isn't run. The
    result is an `unsigned` (C's `size_t`), and is a constant, so it can size an array. An array gives its full size, a
    string literal its length plus 1, and an array parameter 2 (it is a
    pointer);
  - binary `* / % + - << >> & ^ |`;
  - comparisons `< > <= >= == !=`, and `&& || ?:`;
  - assignment `= += -= *= /= %= &= |= ^= <<= >>=`.

  `int` is 16 bits, and arithmetic wraps. `/` truncates toward zero, and
  `>>` of a negative value is arithmetic. Comparisons of `int`s are
  signed, of `unsigned` values and pointers unsigned, and
  comparisons, `!`, `&&` and `||` give 1 or 0, as in C (PLASMA's own
  give `$FFFF` for true). `&&`, `||` and `?:` evaluate only the
  operands C says they do.

  Operations on constants are computed at compile time with these same
  rules, so `-(1 << 4)` and `2 * x + 3 * 4` need no run-time work for
  the constant parts. Code that a constant makes unreachable, such as
  the right side of `0 && f()` or the body of `if (0)` or `while (0)`,
  is not compiled at all. A constant right operand of zero for `/` or
  `%`, or a constant shift count outside 0–15, is a compile error,
  except in such unreachable code. Division by a zero that is only
  known at run time is not checked.
* Digraphs `<% %> <: :>`, `/* */` and `//` comments, and LF, CR or CRLF
  line endings.

Anything else, such as the comma operator, or the types `signed char`
and `long`, gives a "not supported yet" error. (`short` is a synonym
for `int`.)

### Strings and `pstr()`

A string literal is stored as a length byte, the characters, then a
NUL. Its value in C is the address of the first character, as usual,
with type `char *`. `pstr("text")` gives the address of the length
byte instead. That is the PLASMA (length-prefixed) form, which CMDSYS
routines such as `__puts` expect. `pstr()` only accepts a string
literal, and its type is `char *` too. Every string literal has at
most 255 characters, so that each is a PLASMA string as well.

### Calling CMDSYS

A function that is called but not defined in any file linked into the
module must be one of the CMDSYS functions in `cmdsys_sigs[]` in
`src/parse.c` (otherwise the final pass reports an "undefined
reference"). Each has its PLASMA name with `__` in front, such as
`__putc`, `__puts`, `__puti`, `__putln` or `__heapalloc`, so the
standard names stay free for C's own functions (approach.md decision
35). It is imported from CMDSYS by its PLASMA name (`PUTS`). These
are PLASMA's functions with PLASMA's meanings, not C's. For example,
`__puts` takes a PLASMA string and adds no newline, and `__memset`
fills with a 16-bit pattern, so `__memset(p, 'a', 4)` gives `a`, NUL,
`a`, NUL (with 0, as ccish uses it, that makes no difference). The
table gives each one C types, such as `void __puts(const char *)` and
`void *__heapalloc(int)`, and the compiler checks calls against them,
so a mistake is caught at compile time and not at load time. A
pointer that a function only reads is `const` (`__puts`, the source
of `__strcpy`, `__strcat` and `__memcpy`), so passing a `const char *`
needs no cast.

As in PLASMA, a `void` function returns no value, and any other
function returns exactly one.

## Messages

Every error and warning has a number, printed before its text:

```
hello.c:3: error 41: lvalue required as left operand of assignment
```

The text comes from the message file, `ccish.msg`, which the programs
read from their own directory, only when they print a message, so no
message text takes memory (approach.md, "C2 design"). Each line of
the file is a number, a space and the text, in ascending order. If the
file can't be found, only the numbers are printed
(`hello.c:3: error 41 (194):`), and the file explains them.

In the sources, a message is its number, with its text in a comment
right after it, in double quotes:

```c
error(41 /* "lvalue required as" */, NULL);
```

To add a message, give it the next unused number in `ccish.msg` and
write the same text in both places. `make test` runs
`tests/spec/msgs.sh`, which checks that every comment matches the
file, that every number used is in the file and every number in the
file is used, and that the file's numbers ascend.

Messages 262-307 aren't messages but the spellings of C's keywords and
operators, which `cccomp` prints in a message ("expected an expression,
not 'while'"), so that `cccomp` keeps none of them either. A comment
in `src/tokin.c` declares the range ("messages 262-307"), which
`spec/msgs.sh` counts as used.

## Known limits

* Output has only been tested on the C VM (`plvm`), not yet on a 6502
  VM.
* Compilation stops at the first error.
* Limits are fixed sizes, each a `#define` beside its table (those
  several programs share in `src/cclimits.h`, `src/obj.h` and
  `src/ir.h`), set just above what ccish's own source needs, since
  every byte counts on a 64K machine (approach.md, "Table sizes").
  Going past one is a clear error.
  - One function: 1280 bytes of bytecode, 128 calls and data
    references, 104 labels, and 31 `return`s (`MAX_FUNC_CODE`,
    `MAX_FUNC_RELOCS`, `MAX_LABELS`, `MAX_RETURNS`). Each `if`, loop,
    `&&`, `||` and `?:` uses one to four labels.
  - One file: 280 functions (declared, defined or called), 79
    variables visible at once (globals, plus the parameters and locals
    in scope), 401 parameter types in all, 40 distinct types, 6
    struct tags (counting those in blocks that have ended), 32 struct
    members in all, and 203 enum constants and typedef names visible
    at once (`MAX_FUNCS`, `MAX_VARS`, `MAX_PARAM_TYPES`, `MAX_TYPES`,
    `MAX_TAGS`, `MAX_MEMBERS`, `MAX_IDS`). The front end keeps no
    names: the preprocessor numbers them (below).
  - The preprocessor: 8432 bytes of distinct names and file names, a
    length byte each (`MAX_PP_POOL`), 104 macros (`MAX_MACROS`), and
    source lines of 255 characters (`MAX_LINE`); the rest are in
    CCPP.md, "Limits".
  - A string literal: 255 characters, after adjacent ones are joined
    (`MAX_STR`).
  - An identifier: 31 significant characters (`MAX_NAME`); the rest
    are ignored.
  - The back end: 32 operands on its own temporaries in one function
    (`MAX_TEMP_USES`), which only a reordering it can't do by moving
    code uses (4 to 6 each). It keeps no names: it spells them from
    the name file as it writes them.
  - A file name (an output name with its suffix, or the program's own
    directory for `ccish.msg`): 127 characters (`MAX_PATH`), enough for
    ProDOS.
  - A link: 32 objects, and 163 names shared between them, with 1427
    bytes of those names, each with a NUL (`MAX_OBJS`, `MAX_GSYMS`,
    `MAX_GNAMES` in `src/link.c`). `ccrel -l` ends its listing with
    how much of the last two is used. Each object must also fit the
    one-file limits.
* Only a few peephole optimizations so far (see `src/peep.c`): removal
  of unreachable code, plain stores for assignments whose value is
  unused, folded negative constants, adding 0, `INCR`/`DECR`, `ANDI`,
  `IDXW`, `ADDI`/`SUBI` for a byte constant, `ADDLW`/`IDXLW` and the
  other fused adds of a variable,
  multiplication by 0, 1, 3 or a power of two without `MUL`,
  `DLW` for a store followed by a load of the same variable, `LAB` and
  friends for a load or store through a constant address (reading the
  speaker, `*(char *)0xC030`, is `LAB $C030`), and single branch ops
  for tests such as `x == 0`, `x != y` and `!x`. A function with no
  parameters, locals or temporaries has no frame: no `ENTER`, and `RET`
  instead of `LEAVE`.
* Stores need no hidden locals, although PLASMA has no SWAP: for a
  store through a computed address (`*p++ = x`, `*f() = x`,
  `a[i + 1] = x`), the compiler moves the value's code ahead of the
  address's before emitting it. `i + p` is reordered the same way.
  (In an expression too long for the compiler's 64-op buffer, these
  fall back to hidden locals.)
* Compound assignment and `++`/`--` on an object reached through a
  computed address (`*p++ += x`, `(*f())++`), and compound assignment
  to an element with a variable index (`a[i] += x`), need the address
  twice. They save it in
  a hidden local (2 bytes of the 255-byte frame, for that statement
  only), which is 1 byte smaller than computing the address twice and
  computes it once, as C requires.
* A `for` loop with a step clause jumps around the step's code, which
  costs two extra branches per loop (approach.md, issue 17, plans a
  fix).
* String literals in a statement that can never run (such as the body
  of `if (0)`) still take space in the data segment. (In an
  expression that is never run, such as `0 && f("x")` or a `sizeof`
  operand, they don't.)
* Globals without initializers are zero bytes in the module file,
  since PLASMA modules have no uninitialized-data segment, so
  `char buf[4096];` adds 4K to the file. Globals are limited to 32767
  bytes, and string literals to another 32767.
* The listing shows a global by its data offset (`; data+4`), not its
  name.
* Nothing checks evaluation stack depth. Deeply nested calls can
  overflow the VM's 32-entry stack.
